Website audit: Saam's Store

10 September 2026 · prepared by Owais Khan
Pages tested: https://saam-s-store.vercel.app/, https://saam-s-store.vercel.app/shop, https://saam-s-store.vercel.app/products/apple, https://saam-s-store.vercel.app/cart

Summary

We looked at four pages of Saam's Store on 10 September 2026 — the home page, the shop listing, a product page and the cart — testing how they load on a typical mobile phone, what the site tells the public internet about itself, and how the code behind it is put together.

The good news first, because it is most of the story: this is a well-built site. It loads quickly on a phone, it does not jump around while loading, and the parts that usually go wrong on a shop of this kind — the admin area, the checkout, the handling of passwords — are done properly. Nothing we found suggests the site has been attacked, and no customer data was exposed to us at any point.

The one item we would want looked at this week is in the shopping assistant. It is allowed to answer questions by reading the product catalogue, and the code that keeps it to the catalogue can be talked around. Whether that matters depends on a single database setting we cannot see from outside, and checking it takes about a minute — that check is the first thing on the plan below. If the setting is right, this is a tidy-up. If it is not, it is the most important thing in this document.

Beyond that: one thing on the shop page that is quietly costing sales on phones, one protection worth adding before the assistant gets busy, and a short list of standard hardening. In total: 1 high, 3 medium and 1 low-severity item, plus a hygiene list at the end.

Pages were loaded in a real browser with an empty cache, 3 times each, on a Moto G-class Android, 4G profile; the figures below are medians. What is working well

  • Speed is genuinely good. Every page we tested is inside Google's "good" range on all four of its measures, on a mid-range Android phone over 4G. Most shops we look at are not.
  • The page does not shift while it loads. Layout movement measured 0.000–0.001 across every page; anything under 0.1 is considered good. That is the difference between tapping "add to cart" and tapping an advert by accident.
  • The admin area is properly locked. Both the pages and the actions behind them independently check that the signed-in user is the owner, so knowing the address of an admin page is not enough to reach it. This is the single most common serious flaw in shops built on this stack, and it is absent here.
  • HTTPS is set up correctly and strictly, including the header that tells browsers never to try the unencrypted version, with the strongest setting.
  • No secrets are exposed in the code sent to visitors. The one key-shaped value in the JavaScript is Supabase's public "anon" key, which is designed to be there. We decoded it to confirm.
  • Pages are compressed and cached at the edge, which is why the server responds as quickly as it does.

Findings

The shopping assistant can be talked into reading tables it was never meant to see

High Quick fix security

What we found

The chat assistant answers product questions by writing a database query and running it. That is a sound design, and it is deliberately fenced in: a list of three tables it is allowed to touch, and a check that refuses anything else. The check reads the table name that follows each FROM or JOIN, but SQL allows several tables to be listed after a single FROM, separated by commas — and only the first one is ever checked. We ran the site's own safety check against a set of queries to confirm exactly where the line falls:

SELECT * FROM products JOIN orders ON true   -> blocked
SELECT * FROM products WHERE id IN
  (SELECT product_id FROM orders)            -> blocked

SELECT * FROM products, orders               -> ALLOWED
SELECT * FROM products, pg_stat_activity     -> ALLOWED
SELECT pg_sleep(30)                          -> ALLOWED

(“blocked” is the site’s own error: Table not allowed: orders)

The chat box is open to anyone, with no sign-in, and the queries it runs are written by an AI model from whatever a visitor types. So the way in is persuasion, not a crafted request.

Why it matters

This is the layer meant to stop the assistant wandering outside the product catalogue, and it can be stepped around. Whether anything actually escapes depends on one thing we cannot see from outside: what the database account behind the assistant is allowed to read. The design notes in the codebase are careful and correct that this account cannot write anything — that part holds, and it rules out a whole class of damage. But read permission is a separate setting, and nothing in the code records how it was granted. If it can only read the three catalogue tables, this is a broken lock on an interior door and the fix below is a tidy-up. If it can read the tables holding orders, addresses or customer profiles, then a determined visitor could coax customer details out of the chat box, and it becomes the most urgent item here.

How to check which one it is

Run this as the assistant's own database user. It takes about a minute and settles the severity:

SELECT table_schema, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'chatbot_readonly'
ORDER BY table_schema, table_name;

How to fix it

Two changes, and we would do both regardless of what the check above returns:

  1. Make the database enforce it, not the text check. Grant the assistant's account SELECT on exactly the three catalogue tables and nothing else. Then a query that reaches for another table fails in the database itself, whatever wording gets past the application. This is the real fix — the one that does not depend on anticipating every way SQL can be written.
  2. Tighten the check in app/_lib/chatbot/sqlGuard.js so it reads every table in a comma-separated list rather than only the first, and rejects a query with no FROM at all. Keep it — defence in depth is why the two-table trick was the only thing we found — but treat it as the second line, not the first.

Effort

Quick. The permission change is a few lines of SQL; the code change is one function. Budget an afternoon including testing that ordinary product questions still work.

Where

app/_lib/chatbot/sqlGuard.js · app/api/chat/route.js

On phones, the chat button sits on top of the "add to cart" control

Medium Quick fix usability

What we found

The chat bubble is pinned to the bottom-right corner of the screen. On the shop listing at phone width the products are laid out two to a row, each with a round "add to cart" button in its own bottom-right corner — so the chat bubble covers the add-to-cart button of whichever product is at the bottom right of the screen. As the customer scrolls, that is a different product every time. This is visible in the screenshot taken during testing (screenshots/saam-s-store-vercel-app-shop-mobile-above-fold.png): the chat bubble overlaps the cart button on the fourth product tile.

Why it matters

It sits on the one control that starts a purchase, on the page customers browse most, on the device most of them use. A shopper who taps it gets a chat window instead of a product in their basket. Nothing errors, nothing gets logged, and the sale quietly does not happen — which is why this kind of thing survives for months.

How to fix it

Either lift the chat button above the product grid's own controls on small screens, or give the listing extra bottom padding so no tile's cart button lands under it, or hide the bubble while the customer is scrolling the grid. The first is the smallest change.

Effort

Quick. A styling change and a look at it on a real phone.

Where

https://saam-s-store.vercel.app/shop — phone widths only

Main content takes too long to appear (LCP 2.75 s)

Medium Quick fix performance

What we found

LCP 2.75 s — median of 3 cold loads, Moto G-class Android, 4G. Threshold for "good" is 2.50 s.

Why it matters

On Moto G-class Android, 4G, the largest thing on screen finishes drawing after 2.75 s. Google treats anything over 2.5 seconds as poor; it affects both search ranking and how many visitors leave before the page is usable.

How to fix it

Identify the LCP element (recorded in perf.json as `lcpElement`) and shorten its path: serve it at the size it is displayed, in a modern format, without waiting on JavaScript or a render-blocking stylesheet.

Where

https://saam-s-store.vercel.app/cart

Nothing limits how often the chat assistant can be used

Medium Moderate security

What we found

Every message sent to the assistant runs a chain of paid AI calls — working out what was asked, writing a database query, writing the answer, and reading it aloud if voice is switched on. We searched the application for any per-visitor or per-address ceiling on this and found none. There is also no sign-in required to use it.

Why it matters

Two consequences, both about cost rather than data. The first is the bill: anyone can script a loop against the chat box and every message is charged to the store's AI account, with nothing to stop it before the invoice arrives. The second is availability: the assistant holds a pool of five database connections, and the safety check permits a query that simply tells the database to wait. A handful of those in parallel and the assistant stops answering for real customers — the shop itself keeps working, which is why this is medium rather than high.

How to fix it

Add a per-address and per-session rate limit in front of the chat route — Redis is already in the stack for session memory, so the counter has somewhere to live. Pair it with a daily spending cap on the AI account, which is the backstop that works even if the limiter is wrong. Setting a statement timeout on the assistant's database account closes the waiting-query case at the same time.

Effort

Moderate. The limiter is half a day; agreeing the right thresholds takes longer than building it.

Where

app/api/chat/route.js

What we would do first

Before anything else — the one-minute check. Run the permissions query from the first finding. Everything below assumes the answer comes back clean; if it does not, that finding stops being a tidy-up and the order changes, so it is worth knowing before any work is scheduled.

This week. Lock the assistant's database account down to the three catalogue tables, and fix the comma case in the safety check. These belong together — the first makes the rule real, the second keeps the friendly error message — and between them they close the only item here we would call urgent. Add a statement timeout on that same account while it is open; it is one line and it removes the waiting-query trick at the same time. Then move the chat bubble off the add-to-cart button: it is a styling change, and it is the only item in this report that is plausibly costing sales today.

Next. Rate-limit the chat route and put a daily cap on the AI account. This is not urgent while the assistant is quiet, but it wants to be in place before the store is busy rather than after the first surprising invoice — and the cap is worth setting today even if the limiter waits. Alongside it, the four security headers: half an hour of configuration applied once at the edge, and the kind of thing that is easiest to do while nobody is under pressure.

Later, if worth it. The cart page is a quarter of a second outside Google's "good" range on a phone, and everything else is inside it. That is a genuine finding and a small one; it is worth an hour when someone is already in that code, not a scheduled piece of work. The dependency updates in the hygiene list are the same shape — routine maintenance, no known exposure on this site.

The two items in the first paragraph are, together, an afternoon. We would rather do that afternoon and tell you the rest can wait than turn a short list into a long one.

What we did not test

We tested the public storefront and read the source code. We did not sign in as a customer, so the account pages, order history and the checkout beyond its first step are unexamined — on a shop, that is where a meaningful amount of the code lives and we would expect to have more to say about it. We did not attempt any active testing: nothing was submitted to a form, no address was guessed at, and the assistant was not actually prompted into running the queries described above — the safety check was tested directly, in isolation, against the site's own code. Two figures that a report like this often quotes are deliberately absent: we could not verify the HTTPS certificate itself, because our testing setup inspects its own certificate rather than the server's, and the response times below were measured from a data centre close to where the site is hosted, so treat them as a floor rather than as what a customer in Pakistan or Australia experiences. The comparison between pages is sound; the absolute numbers flatter the site.

4 standard security header(s) are not set

Low Quick fix security

What we found

Content-Security-Policy — not present
X-Content-Type-Options — not present
X-Frame-Options / frame-ancestors — not present
Referrer-Policy — not present

Present: HSTS

Why it matters

These headers are the browser-side defences a site opts into. Individually none of them is a vulnerability; together their absence means a bug elsewhere has nothing standing in its way.

How to fix it

Set them once at the edge or in middleware so every response carries them: Start with a report-only policy to find what the site actually loads, then enforce a policy that names the script sources you trust. Send `X-Content-Type-Options: nosniff` on all responses. Send `X-Frame-Options: SAMEORIGIN`, or `frame-ancestors 'self'` in the Content-Security-Policy. Send `Referrer-Policy: strict-origin-when-cross-origin`.

Where

https://saam-s-store.vercel.app/

Dependency updates — routine, with one worth reading twice

Low Quick fix maintenance

What we found

A dependency scan reports eight packages with published advisories, one of them marked critical. We checked each against how this site is actually built and deployed, because that headline number is misleading on its own:

next 16.2.12   "critical" — unauthenticated code execution ... on Windows-hosted servers.
               This site runs on Vercel (Linux). Does not apply.

next 16.2.12   "critical" — code execution in image handling when AVIF is enabled.
               AVIF is not enabled (no `formats` set, so the default WebP applies).
               Does not apply as configured — but do not switch AVIF on before upgrading.

sharp         libvips image-processing advisories. Worth the upgrade: the image
               optimiser accepts images from lh3.googleusercontent.com with no path
               restriction, and that host serves user-uploaded content.

brace-expansion, browserslist, js-yaml, nanoid, postcss
               Build-time and indirect. No path to them from anything a visitor loads.

Why it matters

Not much, today — which is the point of saying so plainly. The two frightening-sounding entries do not apply to this deployment, and reporting them as critical would misrepresent the site. The real content of this item is: upgrade on the normal cycle, and tighten the image-optimiser host list while doing it.

How to fix it

Upgrade next and sharp at the next maintenance window. Add a pathname restriction to each entry in next.config.mjs's remotePatterns so only the store's own image paths can be fetched and resized.

Where

package.json · next.config.mjs

Text is invisible for a moment while the fonts load

Low Quick fix performance

What we found

Three font files totalling 89 kB on the home page (37 kB on the others) are loaded in a way that leaves the text they style blank until they arrive, rather than showing the text immediately in a fallback face.

Why it matters

On a good connection nobody notices. On a slow one the headings are briefly missing on a page that is otherwise already drawn. It is listed here rather than above because the site's measured speed is good and this is at the margin.

How to fix it

Next.js sets font-display: swap by default with next/font; confirm the fonts are loaded through it rather than by a plain stylesheet rule.

Where

All tested pages

No robots.txt and no sitemap

Low Quick fix discoverability

What we found

Both /robots.txt and /sitemap.xml return the site's 404 page. The home page itself is indexable — we checked that it carries no instruction telling search engines to skip it — so this is an omission rather than a block.

Why it matters

Search engines will still find the shop by following links, but a sitemap is how a store tells them about every product page directly, including ones nothing links to yet. On a catalogue that grows, this is the difference between new products appearing in search in days rather than eventually.

How to fix it

Next.js generates both from a file: add app/sitemap.js that lists the product and category pages from the database, and app/robots.js. An afternoon, and it keeps itself current after that.

Where

https://saam-s-store.vercel.app/robots.txt, /sitemap.xml

Some catalogue entries still hold placeholder content

Low Quick fix content

What we found

On the shop listing, the product named "Apple" shows a photograph of a jar of cashew cacao spread and has "Apple" as its entire description; "Chips" shows a bag of chocolate coins; "Neutella Jug" appears to be a misspelling. Screenshots of both pages are in the folder accompanying this report.

Why it matters

This is not an engineering fault and we would normally leave it out — but a shopper cannot tell the difference between test data and a mistake, and mismatched pictures on a shop page cost trust faster than a slow load does. Mentioned once, here, in case the live catalogue was not meant to still hold these.

How to fix it

Review the catalogue in the admin area and remove or complete the sample rows.

https://saam-s-store.vercel.app/shop
